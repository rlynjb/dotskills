# Context quality and requirements

## Required context

Establish the target repository, accessible revision or workspace, and read access to its tree and essential files. If the target is ambiguous or inaccessible, ask for the smallest missing input rather than inventing an onboarding guide.

## Supporting evidence

Inspect applicable repository instructions, README/docs, manifests and lockfiles, configuration, entry points, representative implementation files, tests, and CI/deployment definitions. For the initial Recent Technical Changes section, also inspect available recent commit history and relevant diffs (bounded to substantive code/configuration changes). Treat history as evidence, not proof of runtime behavior; record history/revision limits and inspect affected code/tests when possible. Inspect representative module interfaces and callers for APOSD lessons about information hiding and complexity. Map all major first-party areas at a useful level without reading every file indiscriminately. Treat documentation as claims to compare against implementation; flag conflicts.

## Scope and completion

Preserve the master's three-stage coverage and whole-repository scope, but first present a full Learning Menu of all material planned, evidence-anchored questions grouped across eleven topics. After a representative initial scan of every major first-party area, put a technical, diff-backed **Recent Technical Changes** digest at the very bottom of the Learning Menu; assign `C-xx` identifiers, distinguish verified effects from inferences/unknowns, and wait for the learner to select a question, concept, topic, subsystem, finding, or change. Stage order is optional. **After selection**, teach the four named Alex Xu stages (understand the problem/scope; propose high-level design and validate understanding; design deep dive; wrap up) and choose only **relevant** book lenses from System Design Interview, DDIA, FODE, Algorithmic Thinking and APOSD; never force all five into every step. Guided mode teaches one selected question through all four stages with a worked answer and checkpoint per response; Practice waits for the learner's reasoning one stage at a time; a complete tutorial is available on explicit request. Explain concepts in plain English and omit draft code review comments. Representative flows illustrate the repo rather than replacing its architecture map. State the revision, areas inspected and omitted, unknowns, and access limits. Keep claims grounded in files and symbols, use verified line references only, and distinguish commands inspected, executed, and proposed. Treat the four-step framework as a teaching scaffold applied to existing code, not proof of its original design history; Step 2's buy-in is shared understanding, not permission to modify code. Deliver the final learning summary and practical onboarding path after the applicable stages; label early stopping or incomplete coverage partial. Keep exercises read-only.
